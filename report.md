## Опис предметної області
«ТехноМарт» — український інтернет-магазин побутової електроніки. Магазин купує товари у **постачальників**, розкладає їх за **категоріями**, продає **клієнтам** (фізичним і юридичним особам з різних **регіонів** України). Замовлення оформлюють **співробітники** (менеджери з продажу); у замовленні може бути кілька товарів зі знижками. Склад змінюється автоматично під час продажу/скасування. Окремо ведеться облік користувачів системи, їхніх ролей та журнал дій.

Функціональні вимоги: облік каталогу і залишків; оформлення, відстеження статусів і скасування замовлень; звіти про продажі, ефективність менеджерів, низькі залишки; розмежування прав; журнал змін; резервне копіювання.

## Концептуальна модель
Сутності (11): REGIONS, SUPPLIERS, CATEGORIES, PRODUCTS, EMPLOYEES, CUSTOMERS, ORDERS, ORDER_ITEMS, PRODUCT_PRICE_HISTORY, USERS, ACTIVITY_LOG.
Ключові зв'язки: CATEGORIES 1:N PRODUCTS, SUPPLIERS 1:N PRODUCTS, CUSTOMERS 1:N ORDERS, EMPLOYEES 1:N ORDERS, ORDERS 1:N ORDER_ITEMS, PRODUCTS 1:N ORDER_ITEMS (разом — зв'язок M:N «замовлення — товари» через ORDER_ITEMS), EMPLOYEES 1:N EMPLOYEES (керівник), REGIONS 1:N (клієнти, постачальники, співробітники).

## Реалізація в PostgreSQL
Скрипти виконуються у порядку: `01_create_tables.sql` (DDL з `PRIMARY KEY`, `FOREIGN KEY`, `UNIQUE`, `CHECK`, `NOT NULL`, `DEFAULT`) → `02_insert_data.sql` → `03…08`. Приклад (фрагмент):

```sql
CREATE TABLE order_items (
    order_item_id SERIAL PRIMARY KEY,
    order_id   INTEGER NOT NULL REFERENCES orders(order_id)     ON DELETE RESTRICT,
    product_id INTEGER NOT NULL REFERENCES products(product_id) ON DELETE RESTRICT,
    unit_price DECIMAL(10,2) NOT NULL CHECK (unit_price >= 0),
    quantity   INTEGER NOT NULL DEFAULT 1 CHECK (quantity > 0),
    discount   DECIMAL(4,2) NOT NULL DEFAULT 0 CHECK (discount >= 0 AND discount <= 1),
    UNIQUE (order_id, product_id)
);
```

**Тестові дані** (мінімум 10 на таблицю): regions — 25, suppliers — 10, categories — 10, products — 25, employees — 10, customers — 15, orders — 31, order_items — 47, users — 3.

### Що виправлено у вихідному скрипті
Під час перевірки вихідного SQL-скрипта «ТехноМарт» виявлено й виправлено:
1. **Неправильні `product_id` в `order_items`.** Позиції з id 14–21 посилались на інші товари, ніж зазначено в коментарях (наприклад, «USB-C кабель» мав id 17, а це мікрохвильова піч за 4 999 грн; фактично кабель має id 21). Через це ціна в позиції не збігалась з ціною товару. Усі id перенумеровано відповідно до реального порядку вставки товарів.
2. **Постачальників і співробітників було по 8** — додано по 2 записи (разом 10), як вимагає завдання.
3. **Представлення давали завищені значення.** У `customer_orders_summary` та `employee_performance` `COUNT(o.order_id)` після JOIN з `order_items` рахував позиції, а не замовлення; `avg_order_value` усереднював рядки, а не замовлення; `product_sales_summary` не фільтрував позиції за статусом (умова стояла в `LEFT JOIN orders`, що не відсікає рядки `order_items`). Додано представлення `order_totals` (одна підсумкова сума на замовлення), решту переписано на його основі.
4. Обмеження `CHECK` додавались через `ALTER TABLE` після вставки — перенесено в `CREATE TABLE`; додано `CHECK` на статус замовлення і тип клієнта, `NOT NULL` там, де значення обов'язкове; `ON DELETE RESTRICT` для зв'язків із замовленнями.
5. Виправлено опечатку в email (`bizasystems.ua` → `bizsystems.ua`); дубль індексу по `customers.email` прибрано (`UNIQUE` вже створює індекс).

## Налаштування Docker
`docker-compose.yml` піднімає `postgres:17-alpine` (контейнер `technomart_db`, БД `technomart`, порт 5432) і pgAdmin (порт 5050). Каталог `./database` змонтовано в `/docker-entrypoint-initdb.d`, тому SQL-файли виконуються автоматично в алфавітному порядку (стільки ж префіксів `01…08`). Дані зберігаються в томі `postgres_data`.
```bash
docker compose up -d
docker exec -it technomart_db psql -U postgres -d technomart
docker compose down -v      # повне очищення
```
Підключення з Python: `psycopg2.connect(host='localhost', port=5432, dbname='technomart', user='postgres', password='password')`.

_Скріншоти: `docker compose ps`, підключення через psql/pgAdmin._

| Назва | Призначення | Обробка помилок |

## Тригери (`04_create_triggers.sql`, `07_create_audit.sql`)
| Тригер | Подія | Що робить |
|---|---|---|
| `trg_order_items_stock` | AFTER INSERT/UPDATE/DELETE `order_items` | автоматично зменшує/повертає залишок; не дає продати більше, ніж є |
| `trg_orders_status_guard` | BEFORE UPDATE `orders.order_status` | дозволяє лише рух pending→processing→shipped→delivered, скасування — тільки до відправки; ставить `shipped_date` |
| `trg_orders_cancel_restock` | AFTER UPDATE (статус → cancelled) | повертає товар зі скасованого замовлення на склад |
| `trg_products_price_audit` | AFTER UPDATE `unit_price` | пише старе/нове значення в `product_price_history` |
| `trg_audit_*` (4 шт.) | INSERT/UPDATE/DELETE | журнал `activity_log` у JSONB: хто (з `app.user_id`), що, які поля змінились |

Тригери створюються **після** завантаження тестових даних, щоб історичні позиції не змінювали залишки.

**Перевірка (транзакція з `ROLLBACK`):** замовлення 2×iPhone + 1×PS5 зменшило склад 25→23 та 3→2; спроба замовити 99 PS5 → `Недостатньо товару "PlayStation 5 825GB" на складі: є 2, потрібно 99`; зміна `shipped → pending` → `Неможливо повернути статус з "shipped" на "pending"`; скасування замовлення повернуло склад 23→25; `change_category_prices(8, 10)` змінила 3 товари і створила 3 записи в `product_price_history`.

## Вебзастосунок
Flask + Jinja2. Сторінки: вхід/реєстрація, дашборд, товари, клієнти, замовлення (список, деталі, створення з динамічними позиціями), звіти, журнал, користувачі, бекап. **Валідація на сервері** (`validate_product`, `validate_customer`, перевірка email/телефону/індексу/діапазонів) і **на клієнті** (`static/app.js`: HTML5-атрибути + власні повідомлення, збіг паролів, підтвердження небезпечних дій). Помилки БД (унікальність, FK, CHECK, `RAISE EXCEPTION`) перекладаються у зрозумілі повідомлення.

_Скріншоти: дашборд; список товарів з фільтрами; форма з помилками валідації; створення замовлення; деталі замовлення._

## Розширена функціональність (рівень 3)
- **Аутентифікація й ролі**: реєстрація, вхід/вихід, паролі — bcrypt (`pgcrypto`, `crypt(…, gen_salt('bf'))`), ролі `viewer` < `manager` < `admin` перевіряються декоратором `login_required(role)`; CSRF-токени; адмін керує ролями й активністю акаунтів.
- **Логування**: тригери БД пишуть усі INSERT/UPDATE/DELETE у `activity_log` з `user_id` (передається через `set_config('app.user_id', …, true)` у межах транзакції) + події LOGIN/EXPORT/BACKUP; сторінка «Журнал» з фільтрами.
- **Звіти PDF/Excel**: reportlab (кирилиця через вбудований DejaVu) та openpyxl — каталог, продажі за місяцями, ефективність співробітників, замовлення.
- **Пошук, фільтри, сортування, пагінація**: товари (текст, категорія, діапазон ціни, низький залишок), клієнти (текст, тип, місто), замовлення (клієнт, статус, діапазон дат); сортування за колонками через whitelist.
- **Візуалізація**: Chart.js на дашборді — виручка за місяцями (лінія), за категоріями (кільцева), ТОП-5 товарів (стовпчики), замовлення за статусами; KPI-картки.
- **REST API** з `X-API-Key` (див. README): товари (CRUD), замовлення, статистика.
- **Резервне копіювання**: `backup.py` (pg_dump напряму або через `docker exec`), кнопка в адмінці, `scripts/backup.sh`/`restore.sh`; імена файлів валідуються (захист від path traversal).
- **Індекси** (`08_create_indexes.sql`): індекси на всіх зовнішніх ключах; складений `orders(customer_id, order_date DESC)`; **частковий** для активних замовлень і для низьких залишків; **GIN trigram** (`pg_trgm`) для `ILIKE '%текст%'` по назві товару і клієнта.

План запиту з складеним індексом (історія замовлень клієнта):
```
                                       QUERY PLAN                                        
-----------------------------------------------------------------------------------------
 Index Scan using idx_orders_customer_date on orders  (cost=0.14..8.15 rows=1 width=770)
   Index Cond: (customer_id = 3)
(2 rows)
```
> Примітка: на навчальному обсязі (25 товарів, 31 замовлення) планувальник PostgreSQL для більшості запитів обирає `Seq Scan`, бо читати 1–2 сторінки дешевше за індекс; для наведеного плану використано `SET enable_seqscan = off`, щоб показати, що індекс придатний до використання. Вигоду індексів видно на великих таблицях.

## Автоматичне тестування
Усі SQL-скрипти виконано на чистій БД PostgreSQL без помилок; веб-маршрути перевірено тестовим клієнтом Flask (усі сторінки → 200, CRUD товарів/клієнтів/замовлень, відмова при некоректних даних, 403 для `viewer`, CSRF → 400, API з/без ключа, створення бекапу, PDF із кирилицею).

## Висновки
Створено повний цикл: аналіз предметної області → ER-модель (11 сутностей) → схема в 3НФ → реалізація в PostgreSQL з `CHECK`/`FK`/`UNIQUE` → тестові дані → 17 запитів → 5 процедур, 8 тригерів, 7 представлень → консольний і вебзастосунок → ролі, журнал, звіти, графіки, API, бекап, індекси.
Основні труднощі: невідповідність ідентифікаторів товарів у вихідних даних (виявлена перевіркою цін та коментарів), некоректні агрегати в представленнях через «множення рядків» при JOIN, необхідність створювати тригери після завантаження даних, передача `user_id` у тригери аудиту (розв'язано через `set_config` у транзакції).
